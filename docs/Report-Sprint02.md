# Report — Sprint 02

**Спринт:** SPRINT-02, Smart Gate на реальных данных
**Роли:** работа велась за двоих — ARCHITECT / DS Lead (протокол, причинность, решения) и
ML ENGINEER / SWE (корпус, рантайм, измерения, тесты).
**Главный вопрос спринта:** *воспроизводится ли выигрыш Sprint 01 на настоящих данных —
и если нет, то какое звено каскада является узким местом?*

**Краткий ответ:** не воспроизводится. На реальном корпусе Wikipedia Pageviews
семантический гейт на Qwen3 отбирает кандидатов **статистически неотличимо от случайного
отсева** (гипергеометрический тест, одностороннее `p = 0.175`), а Qwen3-14B не лучше
Qwen3-0.6B ни по одной метрике качества при ×13 стоимости. Решение спринта — **GO-GATE**.

## 1. Executive Summary

| Что | Sprint 01 (синтетика, 60 тем) | Sprint 02 (реальные данные, 305 тем) |
|---|---|---|
| Детектор без гейта | P 0.409 / R 1.000 / FPR 0.619 | P 0.138 / R 0.913 / FPR 0.465 |
| Детектор + Qwen3-0.6B | P 0.722 / R 0.722 / FPR 0.119 | P 0.200 / R 0.304 / FPR 0.099 |
| Прирост precision от гейта | +0.313 | +0.062 (внутри доверительного интервала) |
| PR-AUC (без гейта → с гейтом) | 0.435 → 0.647 | 0.132 → 0.128 |
| Precision@K | 0.200 → 0.600 (K=10) | 0.000 → 0.100 (K=20) |
| Средний lead time | 14.07 → 13.83 | 11.47 → 16.22 |

Три вывода, каждый из которых измерен, а не предположен:

1. **Направление размена сохранилось, величина — нет.** Гейт по-прежнему меняет recall на
   precision (R 0.913 → 0.304, FPR 0.465 → 0.099), но прирост precision +0.062 полностью
   лежит внутри bootstrap-интервала: `[0.087, 0.196]` без гейта против `[0.074, 0.343]` с
   гейтом. Интервалы перекрываются почти целиком.
2. **Отсев неотличим от случайного.** Из 152 кандидатов гейт пропустил 35 и сохранил в них
   7 из 21 позитива. Случайный отсев той же мощности дал бы в ожидании 4.84 позитива;
   одностороннее `p = 0.175`. Это главный результат спринта (раздел 17).
3. **CASE B по PHASE 8.** 14B на парной подвыборке не лучше 0.6B: PR-AUC 0.295 против
   0.323, recall и вся кривая Precision@K совпадают, латентность 25.7 с против 7.3 с на одинаковых промптах (раздел 14).

## 4. Causality / Leakage Controls

Протокол трёх окон: **S (отбор) → O (наблюдение) → L (разметка)**, строго последовательных
во времени.

| Контроль | Как обеспечен | Проверяется тестом |
|---|---|---|
| Отбор сущностей без знания будущего | Универсум берётся из топ-листа окна S, до начала O | `test_realworld.py` |
| Модель видит только O | `Sample.series` собирается исключительно из окна O | `test_regression_sprint02.py` |
| Метки строго после O | Метка считается только по L, окна не пересекаются | `test_regression_sprint02.py` |
| Нет заглядывания вперёд при ранжировании | Скор — максимум статистики на `[0, alarm_index + H]` (DECISION-03) | `test_regression_sprint02.py` |
| База не заражена меткой | baseline = медиана первых 14 дней O, не всего ряда | `test_realworld.py` |
| Пороги не подгоняются под тест | `stage test` падает с `SystemExit` без `frozen_config.json` и ничего не тюнит | `test_sprint02_driver.py` |
| Нет утечки между периодами | Пересечение сущностей dev и test по `entity_key` = **0** | проверено скриптом, см. ниже |
| Нет дублей внутри теста | Дублей `entity_key` внутри test = **0** | там же |

Проверка непересечения:

```bash
PYTHONPATH=src python3 -c "
from smartgate.dataset import load_jsonl
from smartgate.realworld import entity_key
d={entity_key(s) for s in load_jsonl('artifacts/real_world_dataset.dev.jsonl')}
t={entity_key(s) for s in load_jsonl('artifacts/real_world_dataset.test.jsonl')}
print('dev',len(d),'test',len(t),'overlap',len(d&t))"
# dev 329 test 305 overlap 0
```

**Статус утечек: PASS.** Ни один контроль не нарушен; все они закреплены тестами, а не
договорённостью.

выбрать руку, которая ничего не делает. Правило отбора поэтому явное:

```python
alive = {a: d for a, d in llm_arms.items() if d["metrics"]["recall"] > 0}
```

Единственная живая LLM-рука — `llm_series_only`, она и заморожена. То, что она проигрывает
`stats_only` на dev, зафиксировано честно: рука выбиралась среди LLM-рук, потому что
вопрос спринта — про гейт, а не про то, нужен ли он вообще (на этот вопрос отвечает

## 9. 0.6B vs 14B

**Вердикт: CASE B — 14B ≈ 0.6B, гейт остаётся на 0.6B.** Полный разбор с проверкой
контрольного списка CASE C — `docs/QWEN_06B_VS_14B.md`.

Почему не CASE A: 14B не выигрывает ни по одной метрике качества — precision ниже, FPR
выше, PR-AUC ниже, recall и вся кривая Precision@K идентичны. Единственная метрика, где
14B «лучше» — ниже средний lead time, но меньший lead time хуже, а не лучше.

Почему не CASE C (0.6B «лучше» по формальным числам): разница в 1 false positive на n = 40
лежит внутри шума, и контрольный список CASE C пройден — ошибки конфигурации нет:

| Пункт проверки | Результат |
|---|---|
| Один и тот же промпт для обеих моделей | да, общий `build_prompt` |
| Детерминированные настройки | `temperature=0, top_p=1, seed=42, think=false` для обеих |
| Парсинг ответа | JSON-валидность 1.00 на 40/40 у обеих |
| Обрезка ответа лимитом | средний ответ 40.1 токена при `num_predict=256` |
| Контекст | промпт ~974 символа, `num_ctx=4096` |
| Транспорт | `transport_errors = 0` у обеих |

Существенная деталь: согласие по темам — всего **11/20 (55 %)** на руке `llm_series_only`.
Одинаковые агрегаты получаются из **разных** решений, то есть равенство метрик — это не
«две модели сошлись на правильном ответе», а «две модели ошибаются примерно одинаково
часто в разных местах». Ограничение мощности этого сравнения — раздел 15.

### Оговорка: латентность 14B на этом хосте нестабильна

Один и тот же детерминированный набор из 12 промптов, прогнанный трижды, дал для 14B
среднюю латентность **102.4 с → 32.2 с → 25.7 с** (`logs/benchmark*.log`). Что проверено:

* это **не ретраи** — `silent_retries = 0` во всех прогонах, где счётчик уже существовал;
* это **не транспорт** — `transport_errors = 0`;
* скорость генерации между прогонами менялась мало (1.81 → 1.84 → 2.04 ток/с), то есть
  разница не объясняется «машина стала быстрее».

Чтобы различать «модель большая» и «веса подкачивались с диска», в клиент добавлена
разбивка ответа сервера на загрузку / обработку промпта / генерацию — она и приведена в
таблице выше. В последнем прогоне генерация занимает 22.7 с из 25.7 с, загрузка — 0.01 с.
Первый прогон измерить в этой разбивке уже нельзя: артефакт был перезаписан. Поэтому
причина расхождения **не установлена**, и выдавать самое красивое число за истину было бы
нечестно: в таблице стоит последний прогон, а разброс зафиксирован здесь и в бэклоге как
TD-07. На вывод спринта это не влияет — CASE B получен из метрик качества, а по стоимости
14B проигрывает при любом из трёх измерений.

Отдельно измеряется `silent_retries`: `timeout` в клиенте — это таймаут сокета, а не
дедлайн на весь ответ, поэтому истёкшая попытка с последующим успешным повтором может
выглядеть как одна медленная. Счётчик выведен в артефакт, чтобы такую латентность нельзя
было прочитать как время одного вызова; поведение закреплено регрессионным тестом.

Полный артефакт — `evaluation/performance.json`.

## 15. Limitations

Читать обязательно.

1. **Один источник.** Только Wikipedia Pageviews. Вывод «гейт не помогает» строго говоря
   относится к сигналу просмотров, а не к трендам вообще.
2. **Бедный семантический контекст.** Гейт получает заголовок статьи и статистики **того
   же самого ряда** за warmup-окно. Сверх чисел у него только заголовок — настоящего
   внешнего контекста (новости, соцсети) нет. Это самое вероятное объяснение результата и
   первый пункт Sprint 03.
3. **Малое число позитивов.** 23 на тестовом периоде, 17 на dev. Отсюда широкие
   bootstrap-интервалы; различия меньше ~0.15 по precision этим корпусом не различимы.
4. **14B сравнивалась на 40 темах.** При 5 позитивах мощность мала: вывод CASE B — это
   «преимущества не обнаружено», а не «доказано, что его нет». Повтор на GPU на полном
   периоде — пункт S3-05 бэклога.
5. **GPU не измерялся**, а латентность 14B на этом хосте гуляет втрое между прогонами и
   причина не установлена — см. раздел 14.
6. **Разметка — прокси.** «Вирусность» определена порогом по кратности просмотров, а не
   внешним бизнес-событием.
7. **Один запуск на период.** Инференс детерминирован (`temperature=0, seed=42`), поэтому
   повтор даст тот же ответ, но дисперсия по разным seed модели не измерялась.

## 17. Decision

# **GO-GATE**

Полное обоснование — `docs/SPRINT02_DECISION.md`. Коротко:

Ключевая проверка — не сравнение метрик, а вопрос «отличается ли отсев гейта от
случайного?». Детектор выдал 152 кандидата, среди них 21 из 23 позитивов. Гейт пропустил
35 кандидатов и сохранил в них 7 позитивов. Случайный отсев 35 из 152 дал бы в ожидании
`35 × 21/152 = 4.84` позитива. Гипергеометрический тест: одностороннее **p = 0.175**.
Отсев гейта статистически неотличим от случайного.

Почему отвергнуты остальные три варианта:

- **GO-QLOra** — дообучать модель, отсев которой неотличим от монетки, значит
  оптимизировать шум. Сначала нужен сигнал, который стоит учить.
- **GO-QWEN** («гейт хорош, Qwen — узкое место») — гейт **не** хорош: его Precision@K не
  проходит порог 0.50 ни при одном K, а на реальных рядах победил не CUSUM, а простой
  порог, то есть статистическая стадия сама не выжата.
- **NO-GO** — архитектура не опровергнута. Размен recall на FPR идёт в ту же сторону, что
  и в Sprint 01 (FPR 0.465 → 0.099), и не проверена главная гипотеза: гейту ни разу не
  давали настоящего внешнего контекста. Останавливаться, не проверив её, преждевременно.

## 18. Sprint 03 Recommendation

В порядке приоритета:

1. **Дать гейту настоящий семантический контекст.** Сейчас он получает заголовок и
   статистики того же ряда — то есть числа дважды. Без внешнего сигнала «семантический
   гейт» семантику не видит, и раздел 6 это показывает прямо: рука на чистых числах
   единственная живая.
2. **Второй источник данных.** Wikipedia — один канал; вывод не должен зависеть от него.
3. **Починить или удалить `llm_full`.** Рука, отвергающая 100 % кандидатов на обоих
   периодах, — это не консервативный гейт, а сломанный. Причина в промпте или в пороге
   уверенности, и это диагностируемо.
4. **Усилить статистическую стадию.** Победа простого порога над CUSUM означает, что
   дешёвая стадия недонастроена; её улучшение поднимает потолок всего каскада.
5. **Калибровать `confidence`.** Сейчас модель пишет «95 % confidence» на рядах без
   всплеска; без калибровки это поле непригодно для ранжирования.
6. **S3-05: повторить сравнение 0.6B vs 14B на GPU на полном периоде** — снять ограничение
   мощности из раздела 15.
